# database-schema.md — persistent storage

> **What this file is:** current shape of the database(s): tables/collections,
> indexes, and the migration policy. The migrations directory is the
> machine truth; this file is the human/agent-readable map of it, kept in
> sync by the docs-sync rule.
> **Who writes it:** the developer whose change adds a migration (same PR).
> **Who reads it:** anyone writing queries; Architect when reviewing data
> ownership (a table has exactly ONE owning component — see architecture.md).

## Conventions

- PostgreSQL 16. Prisma schema at `api/prisma/schema.prisma`; migrations in
  `api/prisma/migrations/` as checked-in SQL, applied by `prisma migrate
  deploy` from the api container's start command (`docker-compose.yml`) — `docker compose up` on a clean
  volume must arrive at a working schema with no manual step.
- Ids: `uuid` v4 generated by the application, never by the client.
- Timestamps: `timestamptz`, UTC, `created_at` / `updated_at` on every table.
- Naming: `snake_case` tables and columns, plural tables.
- No soft delete: `DELETE /api/cvs/:id` really deletes, by `ON DELETE CASCADE`
  from `cvs`.
- Every foreign key is indexed — PostgreSQL does not do this automatically, and
  an unindexed FK turns every `ON DELETE CASCADE` into a sequential scan. Where
  a composite index below already starts with the FK column, that index counts
  and no second one is created. Every index names the query or cascade it serves.
- Raw SQL is allowed in exactly one place — the job lease (`FOR UPDATE SKIP
  LOCKED`), which Prisma cannot express; everywhere else the typed client.

## Migration policy

- `20261028000000_init` is the first migration. Its CREATE TABLE and index
  statements were generated by `prisma migrate diff --from-empty
  --to-schema-datamodel --script`, then hand-amended in two ways Prisma cannot
  express: `fact_ids` is `NOT NULL DEFAULT '{}'` (Prisma emits a nullable
  `ARRAY[]::UUID[]` default), and the CHECK constraints plus the two partial
  indexes on `generation_jobs` are appended at the end of the file.
- Consequence: `prisma migrate dev` will report drift against the Prisma schema
  on those objects. Do not "fix" the drift by regenerating; edit the SQL and
  keep the two in step. A new migration is a new folder, never an edit to an
  applied one.

## Tables

Seven tables. `framework/docs/domain-model.md` describes six *entities*: the
seventh table, `sessions`, belongs to the User entity and has no separate
business meaning.

## users  (owner: core/auth)

- Columns: `id uuid pk`, `email citext not null`, `password_hash text not null`
  — argon2id, `created_at`, `updated_at`.
- Indexes: `unique(email)` — login lookup and the 409 on register.
- Written by: core/auth; read by: core/auth.

## sessions  (owner: core/auth)

- Columns: `id uuid pk`, `user_id uuid fk→users on delete cascade`,
  `token_hash text not null` — sha256 of the cookie value, `expires_at`,
  `created_at`.
- Indexes: `unique(token_hash)` — the per-request session lookup;
  `(expires_at)` — expiry sweep; `(user_id)` — cascade on user delete.
- Written by: core/auth; read by: core/auth.

## cvs  (owner: core/cv)

- Columns: `id uuid pk`, `user_id uuid fk→users on delete cascade`,
  `title text`, `target_role text not null`,
  `source_kind text not null check in ('pdf','text')`,
  `source_text text not null`, `state text not null check in
  ('generating','ready','failed')`, `version int not null default 1`,
  `last_error_code text null check in (<the C-000 enum, 15 codes>)`,
  `last_error_message text null` (ADR-017/ADR-018: the closed C-000 code and
  its fixed safe message; the CHECK `cvs_last_error_code_check` is in
  migration `20261029010000_cv_last_error_code_check` and is kept equal to
  `ERROR_CODES` by a test; set with state `failed` in the
  same transaction, nulled on regenerate and on success; never a join to
  generation_jobs, a CV outlives its jobs), `created_at`, `updated_at`.
- Indexes: `(user_id, updated_at desc)` — the CV list (C-007), which is the
  only list query in the product.
- Written by: core/intake (insert), core/cv (update), core/jobs (state);
  read by: everyone.

## facts  (owner: core/generation)

- Columns: `id uuid pk`, `cv_id uuid fk→cvs on delete cascade`,
  `kind text not null`, `text text not null`, `source_quote text not null
  default ''`, `source text not null check in ('document','user')`,
  `created_at`.
- Indexes: `(cv_id)` — the verifier loads every fact of a CV at once, and the
  cascade from `cvs`.
- Written by: core/generation (document facts), core/cv (user facts from
  answers and edits); read by: core/generation (verifier), api (C-006).

## cv_items  (owner: core/generation + core/cv)

- Columns: `id uuid pk`, `cv_id uuid fk→cvs on delete cascade`,
  `kind text not null`, `parent_id uuid fk→cv_items on delete cascade`,
  `path text not null`, `order_index int not null`, `data jsonb not null`,
  `fact_ids uuid[] not null default '{}'`, `relevance numeric(4,3)`,
  `user_edited boolean not null default false`, `created_at`, `updated_at`.
- Indexes: `(cv_id, kind, order_index)` — rendering a CV in order, and the
  cascade from `cvs` (it leads with `cv_id`); `unique(cv_id, path)` — the path
  is the addressing scheme questions and patches use, so it must be unique per
  CV; `(parent_id)` — a bullet's cascade when its experience entry is deleted.
- The contact block (ADR-022 Amendment A) is one row of `kind='contact'` at
  `path='contact'`: `data` holds the field values and a per-field `citations`
  map (`{ fullName?: uuid[], email?: … }`), `fact_ids` their union. It is what
  C-006 serves as `contact.citations`.
- Note: `fact_ids` is an array rather than a join table on purpose — items are
  always loaded whole with their CV, never queried by fact; a join table would
  add a migration and a query for no read we actually perform.
- Written by: core/generation (generate), core/cv (edit); read by: api,
  core/export.

## questions  (owner: core/generation)

- Columns: `id uuid pk`, `cv_id uuid fk→cvs on delete cascade`,
  `path text not null`, `text text not null`, `reason text not null`,
  `status text not null check in ('open','answered','dismissed')`,
  `item_id uuid fk→cv_items on delete set null` (ADR-027, migration
  `20261029030000_question_item_binding`: the item the question is about;
  null for a section-level, summary or contact question. The stored `path` is
  the field spelling at write time and is NOT what C-006 serves — the read
  derives the index from the item's current position. The trigger
  `cv_items_unbind_questions` (BEFORE DELETE) nulls `item_id` and rewrites
  `path` to the bare section),
  `answer text`, `answered_at`, `follow_up_of_id uuid fk→questions`,
  `priority int not null default 100`, `created_at`.
- Indexes: `(cv_id, status, priority)` — "open questions for this CV, most
  important first" is the only way this table is read, and it leads with
  `cv_id` so it serves the cascade too; `(follow_up_of_id)` — self-FK cascade;
  `(item_id)` — the unbind trigger's lookup.
- Written by: core/generation (raise), core/cv (answer); read by: api.

## generation_jobs  (owner: core/jobs)

- Columns: `id uuid pk`, `cv_id uuid fk→cvs on delete cascade`,
  `user_id uuid fk→users on delete cascade`, `status text not null`,
  `stage text`, `attempt int not null default 0`, `leased_until timestamptz`,
  `started_at`, `finished_at`, `error_code text`, `error_message text`,
  `input_tokens int`, `output_tokens int`,
  `scope text not null default 'full'`, `scope_path text`,
  `created_at`, `updated_at`.
- Indexes:
  - `(status, leased_until) where status in ('queued','running')` — the lease
    query (`FOR UPDATE SKIP LOCKED`) and the dead-lease reclaim.
  - `unique(cv_id) where status in ('queued','running')` — enforces "at most
    one job in flight per CV", which is what C-010's 409 relies on. It is
    partial, so it does NOT serve the cascade from `cvs`; `(cv_id)` is created
    separately for that.
  - `(cv_id)` — cascade from `cvs`; `(user_id)` — cascade from `users`.
- Written by: core/jobs; read by: api (C-005), core/jobs.
